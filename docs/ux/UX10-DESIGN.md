# UX10 반복 일정·리마인더

상태: V6·반복 UI/발생 준비·기기 API·대기열·암호화 sender/receipt를 배포·검증했다. SW와 기기 설정 UI를 연결하고 저장·수신 정책·프로필/로그아웃을 시험했다. 최종 클라이언트 인수·CI·Pages 배포는 미완료다. UX09의 배포 검증을 마친 다음 시작했다. 아래 각 구현 전 표현은 해당 체크포인트의 설계 기록이며 최신 결과는 UX10-ACCEPTANCE를 따른다.

## 사용자 흐름과 시간 계약

- 기존 할 일 수정에서 반복 안 함/매일/매주/매월, 간격, 시작일, 선택 종료일을 설정한다. 매주는 요일을 선택한다. 매월31일은 31일 없는 달에 생성하지 않으며 마지막 날로 임의 이동하지 않는다.
- 시작·종료 시각과 포함 여유는 기존 규칙을 따른다. 반복으로 여유를 새로 더하지 않는다. 한국 날짜로 발생일을 정하고 실제 알림 예약 때만 UTC로 변환한다.
- 개별 발생 ID는 반복 원본 ID+원래 발생 날짜로 안정적으로 정한다. 개별 날짜를 옮겨도 발생 키는 바꾸지 않는다. 완료·삭제·동기화·재생성이 같은 발생을 중복 만들지 않아야 한다.
- 수정·중단 시 이번만/이후/전체 범위를 명시하고 대상과 날짜를 먼저 보여준다. 완료된 실행 기록은 보존한다. 이번만 건너뛰기는 예외로 기록하여 재생성되지 않게 한다. 개별 수정 예외와 이후의 규칙 변경은 구분한다.
- 목록·오늘·이번 주·시간표·통계·목표는 같은 실제 발생 업무를 사용한다. 원본 템플릿을 업무 합계에 중복 포함하지 않는다. 생성 한도 초과나 잘못된 규칙을 조용히 잘라내지 않는다.

## 데이터와 이전

- 반복 규칙·수정 구간·개별 예외와 안정 발생 참조는 새 V6 계약으로 검증할 계획이다. V1~V5 읽기/백업·이전을 유지하고 V6 저장 후 구버전 쓰기는 원자적으로 거부한다. 기존 업무 ID·원문·시간·목표·분류·실행 취소를 보존한다.
- 임의 선택 날짜마다 전체 계획을 다시 생성하지 않는다. 발생 생성은 안정 키·중복 검사·한도·CAS로 보호한다. 앱이 닫혀 있어도 필요한 반복 발생과 알림을 준비하는 서버 경로를 포함한다.
- 앞으로 1년을 넘는 목록 탐색은 제한된 범위로 계산하고 장기간 반복을 무한 배열로 만들지 않는다. 지원하지 않는 미래 버전/손상 규칙은 원문을 보존해 거부한다.

## 알림 전달과 보안

- 로그인 기기의 명시적 알림 켜기 동작으로만 브라우저 권한을 요청한다. 이번 구현·자체 QA 중에는 실제 사용자 단말의 권한 버튼을 누르지 않는다. 실제 OAuth·알림 허용/거부·실물 단말 전달은 마지막 사용자 인수로 모은다.
- 앱 내부 타이머 안내를 앱 종료 후 푸시 전달로 표시하지 않는다. Service Worker+Web Push 구독, 서버 예약/전달/취소 경로를 구현하고 지원하지 않는 브라우저/권한 거부/오프라인·만료 상태를 안내한다.
- 구독 등록·조회·취소는 인증 사용자 소유 범위로 제한한다. 비밀 키는 서버 전용이고 외부 push endpoint는 허용 공급자·HTTPS·리다이렉트 금지로 제한한다. 외부 주소를 임의 서버 요청으로 사용하지 않는다.
- 업무의 시작·반복·완료·삭제·시각·설정 변경은 오래된 예약을 취소한다. 전달 직전에 최신 계획/버전을 다시 확인한다. 구독 만료·중복 실행·일시 오류·재시도를 구분하고 동시 작업의 lease와 고유 키로 중복 예약을 막는다.
- 유료 계약이나 새 보안 수단의 직접 설정이 필요하면 해당 의존 항목만 최종 사용자 목록에 남기고, 가능한 구현·모사·서버 시험을 먼저 끝낸다.

## ALPEN·타임블로킹과 인수

A: 달력 규칙→V6/이전→범위별 수정·예외→UI→서버 예약/푸시→회귀·배포로 나눈다. L: 집중50분, P: 수정·재검증15분, 외부 대기는 별도다. E: 발생 ID·데이터 보존을 먼저 검증한 뒤 전달을 연결한다. N: 각 블록에서 완료 조건과 다음 실패 사례를 기록한다.

- [x] 매일/주간 요일/매월 간격·시작/종료·윤일·없는 월일·한국 날짜 경계가 명세와 일치한다. (공통 규칙·반복 UI/실제 API 인수)
- [x] 이번/이후/전체 수정·중단·건너뛰기가 지정한 발생만 바꾸며 완료 기록·개별 예외를 보존한다. (UX10-ACCEPTANCE 반복 범위/undo)
- [x] 중복 생성·재접속·CAS·계정 격리·구버전 쓰기·백업/이전/undo를 실제 계정과 서버에서 확인한다. (최종 통합12개·DB/반복 준비 인수)
- [x] 알림 설정·허용/거부/미지원 상태·오래된 예약 취소·실패 재시도·중복 실행을 시험한다. (소프트웨어·브라우저 권한 모사, 물리 권한/수신은 최종 사용자 인수)
- [x] 앱 종료 상태 푸시 경로를 구현하고 모사 증거와 실제 전달 인수를 구분한다. 사람만 가능한 시험은 최종 체크리스트에 유지한다. (서버 Cron/sender·SW/receipt·CLIENT 최종 흐름, 실제 단말 전달 미실행)
- [ ] Q24/Q25/Q28/Q30/Q32, 공통 회귀·CI·배포·동일 SHA 운영 확인 후에만 UX11로 진행한다.

## 확인한 공식 근거

- [MDN Push API](https://developer.mozilla.org/en-US/docs/Web/API/Push_API): Service Worker를 통해 앱이 전면에 없거나 로드되지 않은 상태에서도 서버 메시지를 받을 수 있다. 구독 endpoint는 능력 URL이므로 비공개로 취급한다. 실제 전달은 권한·플랫폼 상태 인수가 필요하다.
- [MDN subscribe](https://developer.mozilla.org/en-US/docs/Web/API/PushManager/subscribe): 사용자 동작에서 구독하고 userVisibleOnly/applicationServerKey를 사용한다. 권한을 자동 요청하지 않는다.
- [Supabase Scheduling Edge Functions](https://supabase.com/docs/guides/functions/schedule-functions): pg_cron+pg_net으로 예약 호출하고 비밀은 Vault로 관리한다. 공개 publishable key를 내부 작업 인증으로 쓰지 않는다. 전송 대기열의 키 접근 위험도 고려해 내부 작업 전용 인증 범위를 검토한다.

공식 페이지 확인일: 2026-10-28. 실제 프로젝트의 확장 설치와 접근 권한을 별도로 확인한 뒤 구현한다.

프로젝트 읽기 확인: pgcrypto1.3·supabase_vault0.3.1 설치, pg_cron1.6.4·pg_net0.20.4 사용 가능하나 미설치다. 비밀 값은 조회하지 않았다. 예약 경로를 구현할 때 확장·RLS/권한·전용 인증을 마이그레이션과 실제 시험으로 추가해야 한다. 현재 이 단계에서 원격 설정을 바꾸지 않았다.

위 문단은 착수 시점의 기준선이다. 아래 서버 구현 이후에는 pg_cron·pg_net이 설치되고 작업이 활성화되어 있다.

## 서버 반복 발생 준비와 예약 호출

- `task-maintenance` Edge와 `oddk-task-maintenance` 분 단위 Cron을 추가한다. 매 호출은 V6 반복 원본이 있는 계정을 사용자 ID 순서로 최대5개 처리한다. 저장된 커서 뒤부터 읽고 끝의 빈 배치에서 처음으로 돌아가므로 앞 계정만 계속 처리하지 않는다. 이 작업은 오늘부터31일의 누락 발생만 준비하며 푸시 전달 작업은 아니다.
- DB가 임의32바이트 티켓을 만들고 해시와2분 만료만 상태에 보관한다. 원문은 pg_net 요청 본문에만 전달한다. Edge가 SHA-256 해시를 계산해 service-role 전용 claim을 호출하면 티켓은 즉시 소모되고45초 lease를 받는다. 외부 Origin·잘못된 형식·위조/재사용/만료 티켓을 거부한다. 브라우저용 API 키나 장기 서버 키를 예약 요청에 넣지 않는다.
- 서버는 공통 V6 검증·한국 날짜·공통 발생 함수를 사용한다. 원래 업무·완료·이동 예외·건너뛰기·목표 연결을 보존한다. 변화가 없으면 저장하지 않는다. 변경이 있으면 동일한 lease와 계정 버전을 확인하는 CAS로만 저장하고 버전은1 증가한다. 다른 기기 변경과 경합하면 덮지 않고 다음 순회에서 재시도한다.
- 배치5개·실행 예산18초·개별 DB 호출6초 제한을 둔다. 손상/상한 초과/쓰기 실패 계정은 원본을 보존하고 결과 개수에 기록한 뒤 다음 계정으로 진행한다. 배치 조회 실패·예산 종료 때는 처리한 마지막 커서를 유지한다. 응답과 작업 결과에는 개수만 남기며 제목·사용자ID·티켓·키를 출력하지 않는다.
- 상태 테이블에는 RLS를 켜고 브라우저 권한/정책을 주지 않는다. claim/batch/write/finish는 service_role만, dispatch는 DB 관리자/Cron만 실행한다. 운영 중지는 state.enabled=false이며 준비된 사용자 업무나 반복 원본을 삭제하지 않는다.

### pg_net의 실제 보안 경계

프로젝트 postgres로 extension 소유 객체의 REVOKE를 실행해도 supabase_admin이 부여한 PUBLIC 권한은 제거되지 않는다. 첫 제한 마이그레이션은 성공 응답 뒤 실제 ACL 검증에서 효과가 없음을 확인했고, 이를 권한 차단 성공으로 기록하지 않는다. 확장을 재설치하거나 관리 역할 권한을 우회하지 않는다.

현재 Data API 노출 스키마는 public·graphql_public이며 net 요청은 비로그인 및 두 시험 계정 모두406/PGRST106으로 거부된다. 앱 소유 상태/RPC도 별도 권한으로 거부된다. 직접 DB에 접속할 수 있는 역할은 pg_net 대기열을 읽고 바꿀 수 있다는 플랫폼 제약이 남는다. 그래서 Vault에서 꺼낸 장기 자격증명을 보내지 않고, 허용된 작업을 한 번 실행하는 짧은 티켓만 사용한다. net 스키마를 Data API에 추가하거나 외부 주소·임의 명령을 받는 dispatch RPC를 공개해서는 안 된다.

공식 근거: [효과 없는 pg_net 권한 회수](https://supabase.com/kb/troubleshooting/revoking-access-to-pg_net-objects-has-no-effect), [요청 대기열의 자격증명 노출 범위](https://supabase.com/kb/troubleshooting/database-roles-can-read-request-headers-queued-by-pg_net). 확인일2026-10-28. 실제 API 격리·티켓 단회성·CAS·운영 상태 증거는 UX10-ACCEPTANCE에 기록한다.

## V6 공통 계약의 구현 결정

- V6 전환은 첫 반복/리마인더 설정 때만 한다. 일반 V5 계획과 V1~V4의 기존 V5 읽기 이전은 유지한다. 전환 전 raw 원문을 계정별 before-v6에 먼저 보존하며 실패하면 새 스냅샷을 쓰지 않는다. 실행 취소는 데이터와 연결을 되돌리되 버전 번호를 V5로 낮추지 않는다.
- 원래 업무 ID는 첫 발생의 별칭으로 보존하고 나머지는 repeat:원본ID:원래발생일을 사용한다. 날짜를 옮겨도 발생 키는 유지한다. 같은 업무를 반복에서 분리하면 해당 원래 날짜를 건너뛰기로 기록해 재생성을 막는다.
- 규칙 변경은 날짜순 구간으로 저장한다. 이후는 원래 발생일을 기준으로 새 구간을 만들며 전체는 시작일부터 일반 미완료 발생을 바꾼다. 완료 기록과 개별 수정 예외를 보존한다. 중단의 이후/전체는 지정 범위의 미완료 발생(개별 예외 포함)을 취소하며 완료 기록은 남긴다.
- 한 번 건너뛰기는 아직 생성하지 않은 유효 발생일에도 기록할 수 있다. 삭제·일괄 삭제도 건너뛰기를 남긴다. 한 날짜의 요약/분할은 그 발생만 반복에서 분리하며 다른 날짜는 그대로 반복한다.
- 분류·태그·목표 삭제는 템플릿의 참조도 함께 정리한다. 기존 발생의 개별 목표 연결은 유지하고 새 발생에는 원본의 목표 연결을 적용한다. 상대 마감은 발생일 전후365일 범위, 시작/종료·여유는 기존 규칙을 따른다.
- 설정 생성/변경은 해당 원본만 주어진 기간에 생성한다. 모든 원본의 주기적인 준비는 별도 유지 경로에서 수행할 예정이다. 조회/생성 범위는366일, 원본100개, 구간64개/원본, 건너뛰기3660개/원본, 실제 업무5000개 한도이며 초과 시 전체 변경을 거부한다.
- reminderMinutes는 없음 또는0/5/10/15/30/60분이며 날짜·시각이 있어야 설정할 수 있다. 이 데이터 검증만으로 푸시 전달이 구현됐다는 뜻은 아니다.

## 기기 구독·관리 API 계약

- `push-subscriptions`는 getUser로 실제 사용자 토큰을 확인하고 config/status/register/disable/devices/revoke만 받는다. 사용자ID 입력은 받지 않는다. 허용 Origin, POST/JSON,4KiB 제한과 엄격한 필드를 검증한다. 브라우저에서 DB 테이블/관리 RPC를 직접 읽고 쓰게 하지 않는다.
- 브라우저 설치마다 UUID와 임의32바이트 deviceToken을 보존한다. 서버에는 `SHA-256(설치ID:토큰)`만 저장한다. 등록/현재 상태/현재 기기 해제에는 이 증명이 필요하다. 같은 브라우저의 계정 전환은 증명을 가진 요청만 소유권을 옮길 수 있고 다른 계정의 이름·구독 주소는 반환하지 않는다.
- 모든 변경은 서버 revision을 대조한다. 미등록 상태에서 해제를 먼저 요청해도 revision1의 비활성 기록을 만들어 뒤늦은 revision0 등록을 막는다. 해제·계정 전환 후 이전 버전의 요청은409다. 동일한 활성 설정을 다시 등록하면 revision이 바뀌지 않는다. 클라이언트는 조작을 직렬화하고 실패 후 최신 상태를 다시 확인해야 한다.
- 계정은 자기 기기 목록의 설치ID·라벨·활성 여부·revision·갱신 시각만 조회하고, 최신 revision으로 잃어버린 기기도 원격 해제할 수 있다. 다른 계정의 기기는 목록에 없고 ID를 알아도 해제할 수 없다. 해제하면 endpoint/암호화 키를 지우고 revision을 올린다.
- 계정당 활성5개·최근 연결 기록20개로 제한한다. 비활성 기록은 지연 요청 방어를 위해30일 보존하며 그 이후 해당 계정의 새 연결/해제 때만 정리한다. 짧은 설정 행 잠금으로 동시 등록에도 개수 제한을 지킨다. 인증 계정 삭제는 FK cascade로 기기 기록을 제거한다.
- 현재 허용 endpoint는 Google FCM·Mozilla·Apple의 HTTPS 고정 호스트/경로다. 임의 호스트·자격증명·포트·쿼리·fragment·인코딩 경로·비정규 URL은 거부한다. 암호화 키는 정규 base64url 길이와 실제 P-256 연산으로 검증한다. 전달부에서도 동일한 주소 검증과 redirect:error를 적용해야 한다.
- VAPID는 서버 WebCrypto로 최초 한 번 생성한다. private scalar는 Vault에 넣고 설정에는 public key와 비밀 참조만 둔다. 초기화 경합은 행 잠금으로 같은 키를 반환한다. API는 공개 키만 반환하며 기기 증명·endpoint·구독 암호화 키·서명 비밀을 응답/로그에 넣지 않는다. 최초 초기화 후 자동 키 회전은 하지 않는다.
- Node는 잘못된 점을 import 단계에서 거부했지만 Deno는 import를 통과시키는 차이를 실제 발견했다. 임시 ECDH 연산까지 수행해 두 환경에서 동일하게 거부한다. 직접 곡선 연산을 구현하지 않는다. 생성한 VAPID 키로 web-push3.6.7의 aes128gcm/VAPID 요청 생성 호환도 로컬 검증했으며 네트워크 전송은 하지 않았다.

남은 클라이언트 정책: 실제 사용자 동작에서만 권한 요청, SW의 계정 바인딩, 로그아웃/계정 전환 시 로컬 수신 차단과 서버 해제, 서비스 미지원/권한 거부/실패 안내를 구현해야 한다. 이 API 배포만으로 실제 알림이 켜졌다고 표시하지 않는다.

## 예약·취소·수신 확인 대기열

- 계획 저장 트리거는 미완료 실행 업무의 reminderMinutes·한국 날짜/시작 시각을 별도 예약으로 투영한다. 요약 업무·미설정·손상 날짜를 제외하고, 완료·삭제·시간/알림 변경 시 이전 예약을 비활성화한다. 같은 업무/시작/알림 시각은 해시 키로 중복되지 않으며 제목만 바뀌면 기존 예약을 유지한다. 시간대별 문자열 표현 대신 epoch를 키에 사용한다.
- 수행 시간에는 기존 여유가 포함된다. 알림 유효 기한은 `시작+2분`, `예약+5분`, `종료` 중 가장 이른 시각이다. 늦어진 시작 알림이나 오래된 사전 알림을 무기한 보내지 않는다. 서버 운영 이력은 만료7일 뒤 정리하지만 사용자 업무·완료 기록은 지우지 않는다.
- 기기 연결/해제·계정 전환 트리거는 현재 소유자와 revision에 맞는 전달 항목만 준비한다. 계획/기기가 동시에 커밋돼 쌍을 놓쳐도 발송 claim 때 다시 보충한다. 보충 쿼리는 이미 대기 중인 행을 INSERT 충돌로 다시 잠그지 않는다. 한 번 표시 확인을 받은 같은 설치/예약은 재연결 revision이 달라져도 다시 준비하지 않는다.
- 한 claim은 최대5개, `FOR UPDATE SKIP LOCKED`와35초 lease로 처리한다. 재시도는5~60초 간격·최대4회다. 오래된 lease는 완료 처리를 못 하며,404/410 구독 만료 결과는 동일 소유자/revision일 때만 기기를 끄고 주소/키를 지운다. 예전 요청이 새 계정 연결을 끄지 않는다.
- 대기열은 제목/메모를 저장하지 않는다. 서버 내부 current RPC가 최신 계획과 구독을 반환하며 공통 currentReminder가 현재 task의 ID·시간·완료·요약·알림 설정을 다시 검증한다. 외부 전송 후 생기는 경합은 브라우저 표시 직전의 수신 확인으로 막을 예정이다.
- claim은 임의32바이트 수신 확인 토큰을 만들고 해시만 저장한다. 향후 암호화 푸시에는 delivery ID·토큰·설치/계정 바인딩만 넣고 제목을 넣지 않는다. 향후 제한된 HTTP 수신 확인 API가 토큰과 로컬 기기 증명을 확인한 뒤 최신 task의 최소 정보만 반환해야 한다. 이미 표시한 항목에는 displayed 상태를 반환하여 중복 표시를 막는다. HTTP 어댑터/Service Worker는 아직 미구현이다.
- 외부 공급자 수락(sent)과 브라우저 표시 확인(displayed_at)은 구분한다. 네트워크 결과가 불확실해 재시도 대기 중이어도 기존 토큰이 유효하고 계획·기기가 그대로라면 수신 확인을 허용한다. 새 claim·취소·계정 전환은 예전 토큰을 무효화한다. 외부 시스템까지 정확히 한 번 전달을 보장한다고 표현하지 않는다.

ALPEN 작업 블록: A 예약 투영/취소→lease/재시도→DB 인수→전송 어댑터→수신/UI로 나눈다. L 집중50분·P 재검증15분 단위로 추정하고 E 데이터 보존·동시성 검증을 먼저 수행한다. N 현재 블록은 DB 경로까지 확인했으며 발송/수신·권한/UI와 최종 배포 게이트가 남아 있다.

## 브라우저 수신과 계정 전환 계약

- 정적 `oddk-push-sw.js`와 core를 사이트 basePath 아래에 배포한다. 앱 캐시/fetch handler는 추가하지 않는다. 설치 proof·계정·revision·세대(epoch)·표시 이력을 scope별 IndexedDB에 보존하며 성공 응답은 request success가 아닌 transaction complete 후에만 보낸다.
- SW 메시지는 scope 안의 실제 WindowClient와 MessagePort를 확인한다. 연결은 현재 epoch를 대조하고 성공할 때 새 세대로 바꾼다. 차단은 사용자/수신 자격을 지우고 세대를 바꾼다. 늦은 bind나 조건부 block은 새 계정 연결을 바꾸지 못한다. 손상 상태는 새 proof로 조용히 덮지 않는다.
- 수신은 엄격한7필드 payload→로컬 기기/계정/revision→서버 receipt→로컬 세대 재확인→표시→표시 이력 commit→ACK 순서다. 표시 중 차단/쓰기 실패는 해당 알림을 닫고 ACK하지 않는다. ACK 실패·중복 푸시는 로컬 이력과 고정 tag로 재표시를 줄인다. 최대500개/7일 이력이며 외부 시스템까지 정확히 한 번을 보장하지 않는다.
- 알림 데이터에 receiptToken/deviceToken이나 원문 메모를 넣지 않는다. 클릭은 현재 계정/세대와 유효 날짜만 확인해 같은 앱 시간표로 이동한다. URL은 내부 고정 경로와 날짜만 포함하고 기존 입력 초안은 유지한다.
- 초기 조회·페이지 재방문·로그인은 권한이나 구독을 자동 요청하지 않는다. ‘내 정보 → 일정 알림’의 버튼에서만 권한을 요청하고 실제 서버 revision 확인 후 로컬 bind를 승인한다. 앱 로그아웃은 로컬 차단 후 서버 정리를 시도하고 SDK signOut을 수행한다. 로컬 차단 실패는 로그아웃을 중지하고, 정리 중 계정이 바뀌면 새 계정을 로그아웃하지 않는다.
- 실제 단말 권한·전달은 최종 사용자 인수다. 자체 시험은 별도 이메일 시험 계정의 실제 API/프로필 동작, 실제 IndexedDB, 권한/구독을 모사한 순수 수신·클라이언트 시험으로 범위를 구분한다.
