# UX11 실제 작업·휴식 기록과 계획 비교

상태: UX10 운영 게이트 완료 후 착수. 계획값을 바꾸지 않는 공통 기록 모델과 전환 규칙부터 구현한다. 아직 실제 기록 UI·DB/API·브라우저 QA·배포는 완료하지 않았다.

## 사용자 흐름

- 기존 할 일에서 ‘작업 시작’ → 일시정지 / 다시 시작 / 휴식 / 기록 종료. 현재 기록하는 일과 시간·상태를 계속 보인다. 종료는 시간 기록 종료이며 업무 완료와 구분한다.
- 일시정지 구간은 작업이나 휴식으로 임의 합산하지 않는다. ‘휴식’을 명시적으로 선택한 구간만 휴식 실적이다. 휴식에서 다시 시작하면 작업으로 전환한다.
- 한 계정/익명 저장소에는 진행 중이거나 일시정지한 기록을 하나만 둔다. 다른 일을 시작하려면 기존 기록의 종료와 새 시작을 미리 확인하고 원자적으로 전환한다.
- 계획 작업/수행 시간은 원본 그대로 두고 실제 작업·휴식·차이를 따로 보인다. 시작 당시 제목·계획 날짜·작업/수행 시간도 기록해 이후 계획 수정/삭제가 과거 실적을 바꾸지 않게 한다.
- 수동 추가·보정은 종료한 기록의 실제 시작/종료·작업/휴식 구간을 입력하고 변경 전후를 확인한 뒤 적용한다. 음수·미래·겹침·상한·원격 변경을 거부하고 초안은 보존한다.

## 데이터·동시성 결정

- V5/V6 계획 JSON과 별도의 실행 기록을 사용한다. 일반 계획 저장/이전/복구가 타이머를 덮거나 원래 계획 시간을 실적값으로 바꾸지 않게 한다. 별도 실적 백업과 보존/복구 범위도 UI에 명시한다.
- 로그인은 사용자 소유 execution state(단일 active record와 monotonic revision), 실행 record(시작 당시 계획 snapshot·최대64구간), idempotency 기록을 DB에 둔다. 서버 전용 테이블/RPC와 getUser 검증 Edge로만 접근한다. 기록 조회는 기간/페이지를 제한하고 합계가 더 보기 범위 때문에 잘리지 않게 한다.
- 상태 변경은 서버 시각·계획 버전·실행 상태 revision·단회 operation ID로 보호한다. 응답 유실 재시도는 같은 조작을 다시 기록하지 않는다. 같은 계정의 두 기기 시작은 하나만 성공하고 다른 쪽은 현재 기록을 확인하게 한다.
- 계획 행 → 실행 상태 순서로 잠근다. 해당 업무 완료/삭제 시 열린 구간을 종료해 유령 타이머가 남지 않게 하고, 다른 업무 수정은 타이머를 바꾸지 않는다. 계획 실행 취소는 기록을 임의 재시작하지 않는다. 삭제한 업무의 과거 실적은 snapshot으로 보존한다.
- 비로그인은 별도 IndexedDB의 commit 완료·원자적 전환으로 보존하고 탭 사이 중복 시작을 막는다. 로그인/로그아웃은 기록 scope를 분리한다. 익명 실적은 사용자 확인 없이 기존 계정 실적을 덮지 않으며 가져오기/백업으로 보존한다.
- 로그인 기록 조작은 서버에 연결된 상태에서 확정한다. 오프라인에는 진행 중 경과 표시와 마지막 저장 시점을 보여주고, 확정하지 못한 조작을 성공으로 표시하지 않는다. 재연결 후 현재 서버 상태를 확인하고 수동 보정 초안은 남긴다.

## 시간 계약

- 실제 시각은 canonical UTC ISO, 계산은 정수 밀리초로 보존하고 화면에서만 초/분으로 표시한다. 종료−시작이 음수가 되거나 구간이 서로 겹치면 거부한다. 열린 구간은 마지막 하나만 허용한다.
- 연속 기록은 시작부터 최대24시간이며, 방치된 기록은 한계 시각에서 닫고 확인 필요로 표시한다. 초과 시간을 계속 누적하거나 계획 시간으로 자동 대체하지 않는다. 사용자가 보정하거나 새 기록을 시작할 수 있어야 한다.
- 자정은 한국 날짜 기준으로 실제 구간을 나눠 합산한다. 작업·휴식·일시정지를 구분하며 pause 구간은 합계에 넣지 않는다. 계획 날짜와 실제 수행 날짜가 달라도 서로 덮지 않는다.
- 같은 업무를 여러 번 기록해도 계획 합계는 업무당 한 번만 집계한다. 실제 합계는 해당 기간의 모든 실제 구간을 합산한다. 개별 기록의 시작 당시 계획 snapshot을 일별 계획 합계에 반복해서 더하지 않는다.
- 수동 보정은 최소1/최대64개의 닫힌 구간을 명시한다. 새로고침·기기 시계 역행·중복 조작·64구간 한도에서도 기존 기록을 보존하고 항상 종료/복구 수단을 제공한다.

## 서버·저장 구현 범위

- 실행 record 한 행에 공통 `ExecutionRecord` JSON과 소유자·검색용 시작/종료 시각을 보존한다. state 한 행에 전역 revision과 active record ID를 둔다. `ended_at IS NULL`인 기록은 일시정지도 포함해 사용자당 하나로 제한한다. 과거 기록은 기간/커서로 조회하며 시간 합계는 페이지에 표시한 행만 더하지 않는다.
- Edge는 getUser 후 서버 시각·최신 계획/버전·현재 실행 상태를 읽고 공통 함수를 적용한다. commit RPC는 계획 행→state 순서로 잠근 뒤 계획 버전/실행 revision과 operation ID를 대조하고 변경된 최대2개 record와 state를 원자적으로 저장한다. 실행 기록 조작은 계획 JSON/버전/updated_at을 바꾸지 않는다.
- 기존 작업을 끝내고 새 작업을 시작하는 switch는 두 record를 함께 저장한다. 응답 유실의 같은 operation 재시도는 원래 적용을 확인하고 최신 상태를 반환하며 두 번 시간을 추가하지 않는다. 오래된 계정·revision·다른 body로 재사용한 operation은 거부한다.
- 업무 완료/삭제 trigger도 계획→실행 state 잠금 순서를 따른다. 열린 구간만 현재 시각(또는24시간 한계)에서 닫고 종료 사유를 기록한다. 다른 업무 편집·실행 취소는 과거 기록을 다시 시작하거나 지우지 않는다.
- 수동 보정은 서버 소유 snapshot을 보존하고 날짜·구간·미래 시각·다른 기록과의 겹침을 검증한다. 보정 중 타이머 상태나 다른 기기 기록이 바뀌면 적용하지 않고 새 미리보기를 요구한다. 비로그인에서도 같은 공통 규칙을 IndexedDB의 단일 readwrite transaction으로 적용한다.
- 계정 간 이력은 섞지 않는다. 익명 실적 가져오기는 사용자가 확인한 닫힌 기록만 중복 ID/내용을 대조해 가져오며 원본을 먼저 백업한다. 실적 백업은 계획 백업과 이름/포함 범위를 명시하고 계획 복구로 실행 state를 임의 덮지 않는다.
