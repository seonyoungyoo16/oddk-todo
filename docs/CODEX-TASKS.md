# oddk 안정화 작업 명세

작성일: 2026-10-27 · 기준 시간대: Asia/Seoul

목표는 현재 개인용 MVP에 날짜별 계획, 일관된 데이터 검증, 반복 가능한 검증 및 배포 절차를 갖추는 것이다. 아래 작업 ID를 지정하면 Codex가 구현 범위와 완료 조건을 확인하고 작업할 수 있다.

이 문서는 실행 명세다. 애플리케이션 코드 수정, 원격 설정 변경, 배포를 수행했다는 뜻은 아니다. 현재 다른 작업에서 동기화와 팝업을 수정 중이므로 T00에서 최신 상태를 재확인한다.

## 작업 대상과 기본 규칙

- 실제 앱 저장소: `C:\workspace\study\todo`
- 로컬 실제 앱: `http://localhost:3000/todo`
- 원격 저장소: `https://github.com/seonyoungyoo16/oddk-todo`
- 기존 배포: `https://seonyoungyoo16.github.io/oddk-todo/todo/`
- `C:\workspace\react_todo\todo`는 별도 랜딩페이지 작업본이다. 이번 작업의 수정 대상으로 사용하지 않는다.
- 저장소와 상위 경로의 AGENTS.md를 읽고, Next.js 변경 전 설치된 `node_modules/next/dist/docs/`에서 관련 지침을 확인한다. Supabase 변경 시 해당 스킬과 현재 공식 문서를 확인한다.
- 기존 사용자 수정과 다른 진행 중인 작업을 보존한다. 전체 초기화, 무관한 파일 교체, 기존 미커밋 변경의 무조건적인 일괄 커밋을 하지 않는다.
- 현재 구현된 동기화와 팝업은 재사용한다. 같은 기능을 새로 만들기 전에 동작 여부와 남은 결함을 확인한다.
- 한 작업의 완료 조건을 충족한 뒤 다음 작업으로 넘어간다. 여러 채팅에서 `page.tsx`, `sync-store.ts`를 동시에 수정하지 않는다.
- 작업별 브랜치와 PR로 변경 범위를 남긴다. 의존 작업은 먼저 완료된 작업 위에서 진행하며, 미완성 날짜 기능이 자동 배포되지 않도록 통합 브랜치에서 관리한다. 배포 가능한 묶음이 완성되면 master 대상 PR로 반영한다.
- 계정 동기화 시험은 격리한 테스트 계정만 사용한다. 실제 사용자 데이터와 인증정보를 시험 자료나 결과물에 넣지 않는다.

## 구현 기본안

다음은 작업을 바로 시작할 수 있도록 정한 설계 기본안이다. 기존에 구현됐거나 사용자가 확정한 요구사항이라는 뜻은 아니다. 별도 변경 지시가 없으면 이 기준으로 구현한다.

| 항목 | 기본안 |
|---|---|
| 업무 수집 | 새 할 일은 제목만으로 추가하며 `plannedDate: null`로 저장한다. |
| 계획 날짜 | `plannedDate`는 실제 존재하는 `YYYY-MM-DD` 또는 null이다. 업무 하나는 한 날짜에 배정한다. |
| 날짜 기준 | 오늘 계산과 날짜 경계는 Asia/Seoul로 통일한다. 선택 날짜는 화면 상태이며 계정 데이터로 동기화하지 않는다. |
| 목록 | 나의 할 일·진행 중·완료는 기존 전체 목록과 전체 진행률을 유지한다. 시간표·ALPEN·통계는 선택 날짜를 사용한다. |
| 시간 | 저장된 `minutes`는 작업+여유의 총시간이다. 작업은 `minutes - bufferMinutes`다. 필드명을 이번에 전면 변경하지 않는다. |
| 유효한 시간 | 시간 미설정은 두 값 모두 null이다. 설정 시 정수이며 `2 <= minutes <= 240`, `1 <= bufferMinutes < minutes`다. |
| 시작 시각 | null 또는 00:00~23:59의 HH:mm이다. 시작 시각이 있으면 시간이 유효해야 한다. 날짜 미지정 상태에서 기존 시작 시각을 보관할 수 있지만 시간표에는 배치하지 않는다. |
| 자정 경계 | 종료가 자정을 넘으면 다음 날 표시를 한다. 통계 귀속은 시작 계획 날짜다. 다음 날로 자동 분할하거나 중복 집계하지 않는다. |
| 완료 상태 | 기존 done을 유지한다. 완료일별 실적, 실제 측정 시간과 실행 이력은 이번 범위에 추가하지 않는다. |
| 통계 | 선택 날짜에 배정된 할 일의 계획 시간을 집계한다. 총 계획에는 완료·미완료를 모두 포함하며 그 기준을 화면에 표시한다. |
| 시간표 | 선택 날짜의 미완료 업무 중 유효한 시간과 시작 시각이 있는 항목을 표시한다. 기존 완료 항목 제외 동작을 유지한다. |
| 하루 점검 | `reviewsByDate[date]`로 분리한다. 기존 날짜 없는 review는 보존하며 임의의 날짜에 귀속하지 않는다. |
| 재계획 | 지난 날짜의 미완료 업무를 자동 이동하지 않는다. 사용자가 새 날짜로 옮길 때 업무 ID·내용·목표 연결·작업/여유는 유지하고 시작 시각은 비운다. |
| 만다라트 | 날짜와 무관한 목표 구조를 유지한다. 날짜 배정과 이월로 업무 ID를 바꾸거나 할 일을 복제하지 않는다. |
| 형식 버전 | Plan에 `schemaVersion: 2`를 추가한다. 서버 동시성용 version과 구분한다. 기존 Plan.start는 호환을 위해 보존한다. |
| 구형 데이터 | 모든 기존 업무는 날짜 미지정으로 옮긴다. 기존 startTime도 보존한다. 기존 일정이 오늘 일정으로 자동 간주되는 일을 막는다. |
| 동기화 | 현재 전체 계획 JSON과 버전 비교 방식을 유지한다. 항목 단위 자동 병합은 도입하지 않는다. |

반복 업무, 포모도로, 실제 소요 시간 측정, 협업 일정, 자동 추천 배치, 새 디자인 전면 개편은 이번 완료 조건에 포함하지 않는다. 앱의 여유 시간 비율을 25%로 강제하지 않는다. 아래 25%는 개발 작업 일정의 예비 시간이다.

## ALPEN 작업 예산과 실행 순서

- L: 구현·시험·수정·기록을 포함한 집중 작업 예산은 합계 18시간이다. AI 응답시간이나 납기 보장값이 아니며 T00과 각 작업 종료 시 재산정한다.
- P: 전체 배정의 25%인 6시간을 예비 시간으로 둔다. 총 배정은 24시간이다. 외부 계정 설정 대기는 별도로 기록한다.

## T00 실제 소스와 검증 기준선 확정

목적: 진행 중인 동기화·팝업 작업과 겹치지 않게 시작점을 고정한다.

- 수정 범위: `docs/verification/BASELINE.md` 신규 작성. 앱 동작 변경 없음.
- HEAD와 브랜치, 미커밋 파일 목록, 실행 포트와 프로세스의 소스 경로를 확인한다.
- 동기화와 팝업의 현재 구현·진행 중·미검증 항목을 구분한다. 다른 작업이 수정 중인 파일은 해당 작업 완료 후 기준선을 다시 확인한다.
- 린트, 타입 검사, 기존 시간 계산 시험, GitHub Pages용 정적 빌드를 실행한다. 현 package.json에 없는 스크립트는 실제 명령으로 기록한다.
- 로컬과 배포 사이트의 커밋/기능 차이를 기록한다. 결과에 인증 토큰이나 실제 업무 내용을 넣지 않는다.

완료 조건: 대상 경로와 HEAD가 명시돼 있고 각 검사의 명령·시각·종료 결과가 있으며, 기존 결함과 이번 작업에서 생긴 결함을 구분할 수 있다. 실패가 있으면 원인을 해결하거나 별도 결함으로 남기고, 영향을 받는 후속 작업을 시작하지 않는다.

## T01 공통 타입과 시간 검증 통합

목적: 화면, 저장소, 서버가 같은 업무와 시간 규칙을 사용하게 한다.

- 기존 파일: `app/todo/page.tsx`, `planning-views.tsx`, `task-time.ts`, `task-time-fields.tsx`, `supabase/functions/plan-sync/validate.ts`.
- 신규 후보: `supabase/functions/_shared/plan.ts`, `tests/unit/task-time.test.mjs`, `tests/unit/plan-validation.test.mjs`.
- 중복된 Task·Priority·Plan 타입과 시간 불변식을 순수 TypeScript 모듈로 추출한다. 브라우저·Node·Deno API와 서비스 키를 공통 모듈에 넣지 않는다.
- 화면의 입력 문자열 파싱은 유지하고, 저장할 데이터의 유효성은 공통 검증을 통과시킨다. 저장 직전 검증과 서버 검증의 의미를 맞춘다.
- `validPlan`은 공통 모듈을 호출하는 어댑터로 둔다. 프런트엔드가 Edge Function의 서버 실행 파일을 import하지 않게 한다.
- 기존 저장 형식과 작업+여유 입력 UX를 유지한다. 날짜 필드는 T04에서 추가한다.

완료 조건 및 시험:

- 총 30/여유 5는 작업 25로 읽히고 재저장해도 총 30이다.
- 총 25/여유 30, 두 시간 중 하나만 설정, 0·음수·소수, 총 241은 거부된다.
- 두 값 모두 null은 허용하고 총 240 경계값을 검증한다.
- 시작 시각만 있고 유효한 시간이 없는 데이터는 거부된다.
- 할 일 제목 길이, ID 중복, 우선순위, 만다라트 구조에 대한 기존 제한이 유지된다.
- Next.js와 Node 시험에서 공통 모듈을 사용할 수 있고 Deno 측 import도 확인된다. 테스트 목적으로 실제 계정에 쓰지 않는다.

## T02 오프라인 시험과 CI 검사 연결

목적: 잘못된 변경이 빌드 성공만으로 배포되는 일을 막는다.

- 수정 범위: `package.json`, 필요한 경우 `package-lock.json`, `tsconfig.json`, `.github/workflows/`, `tests/unit/`, `tests/README.md`.
- `test`, `typecheck`, `test:integration`을 구분한다. npm test는 외부 통신과 비밀정보 없이 실행되는 단위시험만 포함한다.
- `typecheck`는 설치된 Next.js의 타입 생성 명령을 먼저 실행하고 tsc를 실행한다. 생성 파일을 직접 작성하지 않는다.
- 기존 시간 시험을 단위시험 경로로 옮기고 이후 작업의 시험도 같은 명령으로 실행되게 한다.
- 두 계정 동기화 시험은 별도의 통합시험 명령에만 포함한다. 인증 fixture가 없으면 필요한 설정을 명확히 알리고 실패한다. 통합시험을 실행하지 않고 통과로 기록하지 않는다.
- PR에 설치·린트·타입 검사·단위시험·Pages 정적 빌드를 연결한다. master 배포도 같은 검사 통과 후 실행한다. PR 검사에서 배포하지 않는다.
- Deno 실행 파일과 브라우저 공통 모듈의 검사 범위를 구분하고, 디렉터리 전체 제외로 공통 모듈의 오류를 숨기지 않는다.

완료 조건: 깨끗한 체크아웃과 Node 24에서 오프라인 시험이 실행되고, 의도적으로 불변식 시험을 깨뜨리면 CI가 실패한다. 정상 복구 후 모든 검사가 통과한다. 인증 fixture·생성 실행파일은 커밋되지 않는다.

## T03 서버 검증과 DB 쓰기 경로 보강

목적: API 또는 DB 직접 쓰기로 업무 규칙과 버전 비교를 우회하지 못하게 한다.

- 수정 범위: `supabase/functions/plan-sync/account.ts`, `validate.ts`, `supabase/account-schema.sql`, 필요 시 새 마이그레이션, `tests/account-sync.test.mjs`, 서버 경계값 시험.
- 현재 프런트엔드가 쓰기를 Edge Function으로만 수행하는지 먼저 확인한다. 이 기본안에서는 Data API의 authenticated 직접 INSERT/UPDATE를 허용하지 않고, Edge Function의 서버 권한으로만 검증 후 쓴다. 소유자 SELECT와 RLS는 유지한다.
- 서버 공통 검증을 ensure·push에 적용한다. 잘못된 JSON/본문은 400, 용량 초과는 413, 인증 실패는 401, 버전 충돌은 409로 구분한다.
- 본문의 user_id를 신뢰하지 않고 검증된 로그인 사용자 ID만 사용한다.
- 버전 조건 불일치 시 plan·version·updated_at이 바뀌지 않게 한다. 초기 ensure 동시 요청도 같은 계정의 기존 내용을 덮지 않게 한다.
- DB 변경이 필요하면 현재 Supabase 스킬의 절차로 마이그레이션을 생성하고 검증 환경에서 먼저 적용한다. 프런트엔드 배포와 DB/Function 반영 결과는 별도로 기록한다.

완료 조건 및 시험:

- T01의 모순된 시간 값은 API에서 400이며 DB 내용과 version이 유지된다.
- 같은 계정의 정상 push만 반영되고 다른 계정의 데이터는 조회·수정되지 않는다.
- 익명 및 일반 로그인 사용자의 직접 INSERT/UPDATE가 차단된다. 기존 시험의 기대값을 새 권한 모델에 맞춘다.
- 정상 API 저장, 소유자 조회, 동시 저장 충돌은 계속 동작한다.
- 기존 사용자 데이터 손실 없이 검증 환경 적용을 확인하며 운영 반영은 해당 배포 단위에서 수행한다.

## T04 날짜 스키마와 기존 데이터 이전

목적: 기존 업무를 보존하면서 날짜별 계획을 저장할 수 있게 한다.

- 수정 범위: 공통 Plan/Task 모델, `app/todo/page.tsx`의 readPlan, `initial-plan.json`, 저장소 읽기 경계, `tests/unit/plan-migration.test.mjs`.
- 추가 필드: `Plan.schemaVersion = 2`, `Task.plannedDate`, `Plan.reviewsByDate`.
- 계획 날짜의 실제 달력 유효성을 검증한다. `2026-02-30`, 형식만 맞는 잘못된 날짜, 비문자열은 거부한다.
- 버전 없는 기존 Plan을 V1으로 인식하고 V2로 변환하는 순수 함수를 만든다. 미래의 알 수 없는 버전은 임의로 변환하지 않는다.
- 기존 업무 ID·제목·시간·시작 시각·완료·우선순위·만다라트를 보존하고 plannedDate를 null로 둔다. 기존 review도 날짜 없는 원문으로 보존한다.
- 로컬 원문을 덮어쓰기 전에 별도 백업 키에 보존한다. 새 값과 원문 백업 저장이 안전하게 끝나기 전에는 원문을 삭제하지 않는다.
- 계정 캐시도 같은 변환 함수를 사용할 수 있게 하되, 원격 전송과 구형 클라이언트 처리는 T08에서 연결한다.
- JSON 파손이나 필수 필드 오류에서 초기 데이터로 조용히 덮어쓰지 않는다. 원문 보존과 복구 안내 상태를 제공한다.

완료 조건 및 시험: V1→V2에서 날짜 이외의 기존 값과 참조가 유지되고, 두 번 실행해도 결과가 같다. 잘못된 JSON·저장 실패·미래 버전에서 원문이 남는다. 빈 계획과 기존 목표가 있는 계획을 모두 시험한다.

## T05 날짜 선택과 업무 날짜 배정 UI

목적: 수집한 할 일을 특정 날짜의 계획으로 편성한다.

- 수정 범위: `app/todo/page.tsx`, 기존 작업 수정 팝업, 필요 시 작은 날짜 선택 컴포넌트와 CSS, 날짜 유틸리티 시험.
- 시간표·ALPEN·통계에 공통 선택 날짜와 오늘 복귀 기능을 제공한다. 새로고침 시 오늘의 한국 날짜를 사용한다. 전체 목록 필터의 의미는 바꾸지 않는다.
- 수정 팝업에 계획 날짜 선택·오늘로 지정·날짜 해제를 추가한다. 새 업무의 빠른 추가는 제목만으로 가능하게 유지한다.
- 날짜를 지정하지 않은 항목은 시간 설정을 보관하더라도 시간표에 표시하지 않는다. 기존 데이터에는 날짜 재배정이 필요함을 간결하게 안내한다.
- 저장 실패 시 팝업의 입력과 선택 날짜를 유지한다. 취소하면 기존 데이터가 유지된다.
- 서버 렌더와 브라우저 최초 화면에서 날짜 차이로 hydration 오류가 생기지 않게 한다.

완료 조건: 오늘·내일 업무를 각각 배정하고 새로고침해도 유지된다. 날짜 해제와 취소가 정상 동작한다. UTC 날짜가 한국 날짜와 다른 경계에서도 오늘이 맞다. 키보드로 날짜 입력·저장·닫기가 가능하고 브라우저 증거를 남긴다.

## T06 날짜별 시간표 ALPEN 통계 연결

목적: 세 화면이 선택 날짜와 동일한 계산 규칙을 사용하게 한다.

- 수정 범위: 날짜별 selector, `page.tsx`, `planning-views.tsx`, `timeline.ts`, `tests/unit/day-selectors.test.mjs`, `timeline.test.mjs`.
- 날짜별 업무 선택·계획 시간·완료 수·미설정 수를 순수 selector로 추출한다. 화면마다 유사한 필터를 따로 만들지 않는다.
- 시간표는 선택 날짜의 미완료/시간 설정/시작 시각 설정 항목만 배치한다. 겹침·빈 구간·작업/여유 구분을 유지한다.
- ALPEN의 업무 수·시간·우선순위·배치 수를 선택 날짜 기준으로 계산한다.
- 통계의 총 계획은 완료 포함, 완료 시간은 완료한 업무의 계획 시간으로 표시한다. 실제 소요 시간으로 표현하지 않는다.
- 선택 날짜가 오늘이 아니면 제목과 날짜를 함께 표시해 오늘 통계로 오인하지 않게 한다. 전체 목록의 진행률은 유지한다.

완료 조건 및 시험:

- 오늘 A(총 60/여유 10), 내일 B(총 30/여유 5), 날짜 없는 C를 넣으면 오늘 통계는 60/50/10, 내일은 30/25/5다. C는 일별 집계에서 제외된다.
- A 완료 후 오늘 총 계획은 60, 완료 업무의 계획 시간은 60이며 시간표에서는 빠진다.
- 연속 일정은 겹침으로 처리하지 않고, 실제 겹침은 나란히 보인다.
- 23:30 시작 총 60분은 다음 날 00:30 종료로 표시하고 시작 날짜에 한 번만 집계한다.
- 새로고침과 화면 전환 뒤에도 세 화면의 수치가 일치한다.

## T07 재계획과 날짜별 하루 점검

목적: 지난 날짜의 미완료 업무와 점검 내용이 다음 날짜와 섞이지 않게 한다.

- 수정 범위: 재계획 함수/컨트롤, ALPEN 점검 폼, 날짜별 review 모델, 관련 단위시험.
- 지난 날짜의 미완료 업무에 새 날짜로 재계획하는 동작을 제공한다. 기존 목록 필터를 임의로 일별 목록으로 바꾸지 않는다.
- 재계획은 같은 업무의 plannedDate만 변경하고 startTime을 null로 만든다. ID·총시간·여유·우선순위·만다라트 연결을 유지한다.
- 날짜가 바뀌었다는 이유로 데이터를 자동 이동하지 않는다. 완료 업무는 미완료 재계획 대상으로 선택되지 않게 한다.
- 점검은 선택 날짜에 저장한다. 기존 날짜 없는 점검은 별도 표시하며 임의로 오늘 점검에 넣지 않는다. 사용자가 날짜를 지정해 옮길 때만 해당 날짜에 반영한다.
- 날짜 전환 시 작성 중인 점검이 사라지지 않게 한다. 날짜별 초안을 유지하고 저장 대상 날짜를 명확하게 표시한다.
- 동기화로 원격 점검이 바뀌어도 편집 중인 초안을 덮지 않는다. 변경 사실과 저장 전 선택 방법을 제공한다.

완료 조건: 어제 업무를 내일로 옮겨도 중복 업무가 생기지 않고 목표 연결이 유지된다. 어제·오늘 점검이 독립 저장된다. 날짜 전환과 원격 수신 중에도 미저장 입력을 잃지 않는다. 저장 실패 후 재시도가 가능하다.

## T08 스키마 이전과 동기화 호환 처리

목적: 새 날짜 형식, 기존 서버 데이터, 구형 클라이언트가 만날 때 데이터를 보호한다.

- 수정 범위: `sync-store.ts`, `sync-panel.tsx`, 공통 이전/검증 모듈, Edge Function, 동기화 단위·통합시험.
- 현재 구현된 버전 비교, 오프라인 대기, 계정별 캐시, 충돌 선택, 백업을 재사용한다.
- 서버가 V1이면 새 클라이언트에서 V2로 이전하고 기존 version을 조건으로 저장한다. 다른 기기가 먼저 저장했으면 409 충돌 경로로 처리한다.
- 서버에서 V2 저장 후 V1 클라이언트의 push로 날짜 정보가 제거되지 않게 한다. 형식 퇴행 요청은 426과 새로고침 안내로 거부하고 원본을 유지한다. 형식 버전과 동시성 version을 혼동하지 않는다.
- 서로 다른 날짜의 수정도 전체 계획 JSON 충돌임을 유지한다. 자동 병합하지 않고 두 내용 비교·선택·선택 전 백업을 보장한다.
- 로그인·로그아웃·계정 전환·통신 중 추가 편집·새로고침에서도 다른 계정 캐시와 미전송 변경이 섞이지 않게 한다.
- 잘못된 원격 데이터나 알 수 없는 버전 수신 시 마지막 유효 데이터와 미전송 내용을 보존한다.
- 단위시험에서는 네트워크를 대체하고, 실제 서버 시험은 테스트 계정으로 별도 실행한다.

완료 조건: V1 계정 첫 접속, V2 재접속, 오프라인 수정, 재연결, 두 기기 충돌, 전송 도중 추가 편집을 시험한다. 구형 push가 V2를 덮지 못하고, 선택하지 않은 내용도 백업으로 남는다. 적용 전후 원격 version과 계획 내용을 대조한다.

## T09 인증과 기기 간 동기화 인수시험

목적: 구현 코드 보유와 실제 로그인·동기화 성공을 구분해서 확인한다.

- 수정 범위: `tests/account-sync.test.mjs`, `account-store.test.mjs`, 발견된 동기화 결함의 최소 수정, `docs/verification/SYNC-ACCEPTANCE.md`.
- 각 OAuth 제공자의 현재 설정·지원 상태를 확인한다. 이미 완료된 설정을 새로 만들거나 교체하지 않는다.
- GitHub와 Google은 각각 로그인 시작→콜백→앱 복귀→저장 데이터 반영까지 확인한다. 제공자별 미완료 상태를 숨기거나 서로의 성공으로 대체하지 않는다.
- 격리된 브라우저 프로필 두 개와 동일한 테스트 계정으로 할 일·날짜·만다라트·하루 점검의 상호 반영을 확인한다. 실제 기기를 쓰지 않았다면 두 실제 기기 시험이라고 기록하지 않는다.
- 별도 테스트 계정으로 데이터 격리, 인증 만료, 로그아웃 후 로그인 전 목록 복원을 시험한다.
- 오프라인 수정→재시작→재연결, 동시 수정→충돌 선택→반대쪽 반영을 확인한다. 폴링 주기와 통신 대기를 고려해 제한 시간 내 일치 여부를 기록한다.
- 실제 OAuth를 시험할 수 없는 경우 해당 항목은 외부 의존 미완료로 기록하고 일반 비밀번호 로그인 시험으로 성공을 대체하지 않는다. 독립적인 서버·저장소 시험은 계속 진행한다.

완료 조건: 시험별 기대값·관측값·서버 상태 대조·결과가 있고 로그인부터 양쪽 반영까지 확인됐다. 시험용 레코드는 정리한다. 인증정보는 결과에 포함하지 않는다. 남은 제공자가 있으면 해당 제공자 기능은 배포 완료 범위에서 제외하고 실제 UI도 준비 중으로 표시한다.

## T10 전체 브라우저 인수시험

목적: 기존 기능과 날짜 기능을 한 사용자 흐름으로 검증한다.

- 수정 범위: 발견된 결함의 최소 수정, `docs/verification/ACCEPTANCE.md`, 필요한 화면 증거.
- 시험 순서: 제목만 추가→중복 차단→수정→시간 설정→오늘 배정→시간표 확인→만다라트 연결→ALPEN 이동→점검→완료→통계→새로고침.
- 별도 시험: 필터 범위 전체선택, 일괄 완료/취소, 일괄 삭제/복원, 날짜 변경, 미완료 재계획, 자정 넘김, 저장 실패 입력 보존.
- 라이트/다크 모드, 키보드 조작과 팝업 포커스, 데스크톱 및 390px 모바일 폭에서 확인한다. 모바일 실기기 결과는 별도로 구분한다.
- 브라우저 콘솔의 예상하지 않은 오류, hydration 오류, 초기화로 인한 데이터 소실이 없어야 한다.
- 새 프로필에는 기존 초기 목표 이외의 시험용 할 일을 미리 넣지 않는다. 시험 자료와 실제 업무를 분리한다.
- 결함을 수정하면 관련 시험을 다시 수행한다. 이전 화면의 통과 결과로 새 구현의 통과를 대신하지 않는다.

완료 조건: 각 시나리오의 기대값·결과·실행 환경·증거를 기록하고 차단 결함이 없다. 시험 후 남은 데이터와 설정을 원래 상태로 되돌린다. 실행하지 못한 환경은 미검증으로 남긴다.

## T11 배포 문서와 배포 후 검증

목적: 검증한 코드와 실제 배포된 코드, 백엔드 구성을 일치시킨다.

- 수정 범위: `README.md`, `docs/RELEASE.md`, 필요한 배포 워크플로, `docs/verification/RELEASE-ACCEPTANCE.md`.
- 실행·시험·배포 명령, 데이터 형식, 날짜 귀속·이월 규칙, 초기 데이터·로컬/계정 데이터 관계를 최신화한다.
- UI 기본안의 날짜 규칙과 실제 구현을 대조한다. 실제 측정 시간이 없다는 설명을 유지한다.
- 프런트엔드 커밋, Edge Function 버전, DB 마이그레이션 상태를 각각 기록한다. 검증용 계정과 fixture 생성·정리 방법은 비밀값 없이 문서화한다.
- 배포 순서는 구형/신형 데이터를 모두 안전하게 받는 백엔드→CI 통과한 프런트엔드→배포 환경 인수시험이다. Pages 성공만으로 백엔드 적용 완료로 판단하지 않는다.
- 롤백 시에도 V2 데이터가 V1 화면 저장으로 제거되지 않게 한다. V2 읽기를 지원하는 직전 호환 버전으로 되돌리거나 동기화 쓰기를 중단하는 대안을 문서화한다. 데이터를 구형으로 자동 역변환하지 않는다.
- 통합 PR의 검사와 실제 Pages 배포 성공을 확인하고, 배포 URL의 경로·로고·OAuth 복귀·오늘 계획 저장·다른 프로필 반영을 확인한다.
- 인증 공급자 또는 실제 기기 시험에 미완료가 있으면 배포 기능 범위와 잔여 항목에 반영한다.

완료 조건: 배포 커밋과 백엔드 구성이 추적 가능하고, 배포 환경에서 핵심 흐름이 동작하며, 복구 절차와 잔여 검증이 기록돼 있다. 단순 문서 수정에 구현을 따라 하는 별도 단위시험을 추가하지 않는다.

## 공통 완료 보고 형식

각 작업의 결과는 다음 형식으로 남긴다. 체크박스는 실제 조건을 충족한 뒤에만 변경한다.

```text
작업 ID:
상태: 대기 / 진행 / 검증 대기 / 완료 / 외부 의존 대기
기준 커밋과 변경 파일:
변경한 동작:
완료 조건별 결과:
실행한 시험과 결과:
브라우저 및 원격 검증 범위:
PR 및 배포 커밋 또는 미배포 사유:
예상 집중 시간 / 실제 집중 시간 / 외부 대기:
남은 결함과 다음 작업:
```

후속 Codex 요청 예시:

```text
C:\workspace\study\todo\docs\CODEX-TASKS.md를 읽고 T00을 진행해줘.
실제 앱 소스와 진행 중인 변경을 먼저 확인하고, 기존 변경을 보존해줘.
명세의 산출물과 완료 조건을 채워서 결과를 보고해줘.
T00에서는 기준선 문서만 작성하고 기능 구현은 시작하지 마.
```

```text
C:\workspace\study\todo\docs\CODEX-TASKS.md의 T01을 구현해줘.
T00의 완료 여부와 최신 소스를 확인하고 기존 팝업·동기화 변경을 보존해줘.
명세 범위 안에서 구현, 관련 시험, 브라우저 확인까지 마치고 완료 조건별 결과를 보고해줘.
이미 구현된 부분은 재작성하지 말고 검증해서 남은 부분만 보완해줘.
```
